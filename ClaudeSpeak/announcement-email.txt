Subject: ClaudeSpeak - having Claude Code read its replies through your screen reader


I have been doing a lot of development work with Claude Code, and the thing that
slowed me down most was not the AI. It was reading the output.

In my experience both the Claude desktop app and the terminal have challenges
with screen readers. The desktop app often requires scrolling around in a screen
reader's view of the text, using scroll to bottom, and generally fishing around
too much to find what was just said. The terminal, when a screen reader is set to
echo back terminal output, rereads all sorts of terminal output, even while you
are entering new commands.

ClaudeSpeak is aimed at improving on both situations. It makes Claude Code speak
each reply once, cleanly, as soon as it finishes - and it can speak through your
screen reader rather than around it.

https://github.com/kellylford/TheWorkBench/tree/main/ClaudeSpeak

It costs nothing in Claude usage. The text is pulled out of the session
transcript by a hook, so the model is not involved and no extra tokens are spent.
Asking Claude to read its own replies does cost tokens, because the text has to
be generated a second time.

JAWS exposes a COM interface and NVDA has a controller client library. Going
through either means Claude's replies use the voice, rate and punctuation level
you already configured, and your usual silence key interrupts them like any other
speech. Nothing new to learn. If you would rather have a separate Windows voice
so Claude is distinguishable from everything else, that works too and is a config
setting.

Setup is two PowerShell scripts and about ten lines in a settings file. With no
configuration at all it speaks through whichever screen reader is running, and
falls back to a Windows voice if none is. It applies to every Claude Code session
on the machine - the desktop app as much as the terminal.


TWO THINGS THAT COST ME AN AFTERNOON

Both JAWS and NVDA are verified working. Getting NVDA there turned up two traps
that I have not seen written down anywhere, so they are worth passing on even if
you never use this project.

First, the NVDA controller client DLL does not ship with NVDA. I confirmed this
on 2026.1.1 - nothing matching nvdaControllerClient exists anywhere under the
install directory. You get it from NV Access's controller client package, which
is a separate 4.5 MB download.

Second, and this is the one that had me convinced my code was wrong: the DLL has
to match the architecture of the process calling it, not of NVDA and not of
Windows. I am on Windows on ARM. The inbox PowerShell there is ARM64 native, and
SysWOW64 is x86, so there is no x64 PowerShell unless you install one - and x64
is exactly the build you are most likely to already have lying around. Loading it
throws BadImageFormatException. The package contains x86, x64, arm64 and arm64ec
builds; you want the one matching PowerShell.

Do not trust the filename either. NV Access shipped the ARM64 library as
nvdaControllerClient32.dll for a while, and the arm64ec build reports x64 in its
PE header. The scripts here read the header rather than the name.

A third one, more general: the engine falls back to another route when the
configured one fails, so speech happening does not prove your route worked. A
failing NVDA config fell through to a Windows voice and sounded exactly like
success - twice. There is now a log recording which route actually spoke. If you
test this, check the log rather than trusting your ears. I would not have caught
it otherwise.


WHERE I COULD USE HELP

- NVDA is verified on ARM64 Windows. Plain x64 should be the easier case, but
  nobody has actually run it there. If you use NVDA on x64, five minutes would
  confirm it.

- If you know NVDA's controller client well, I would welcome a second opinion on
  whether P/Invoking the DLL is even the right approach.


ALSO WELCOME

- Narrator, VoiceOver and Orca are not wired up at all.
- Windows is much better developed than the macOS and Linux version, which uses
  say and spd-say.
- The markdown-to-speech handling drops code blocks and tables and reads URLs as
  the word "link". Those are my guesses about what people want to hear, not
  anything I have tested with anyone else. I would particularly like to be told I
  got these wrong.

There is also a Claude Code skill included that walks you through picking a route
and voice conversationally. It checks what is actually installed rather than
assuming, and lets you audition voices before committing.

Suggestions, corrections, pull requests and disagreement about the design choices
are all welcome. Issues and PRs on the repo, or just reply here.
